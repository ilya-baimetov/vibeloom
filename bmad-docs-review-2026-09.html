Verdict

The v6.11 docs are much better than the community folklore says. A January 2026 audit logged 47 doc issues and newcomers filed "confusing and sometimes incorrect". What exists today — a task-first restructure, a real style guide, CI link validation, zero naming drift after aggressive renames — is the strongest docs discipline I've seen in an OSS AI framework.

The gaps that remain are specific and fixable: the flagship theory page makes precise empirical claims with zero citations, the reference tier is one page for 29 commands, translations are a full information-architecture generation behind English, and the site carries no version signals. Details and receipts below.

What's working — worth saying out loud

  • The restructure was the right call, executed with discipline. Diátaxis buckets became user journeys, and the old URLs didn't break: 58 redirect rules in astro.config.mjs. The "Find Your Starting Point" router on the homepage is exactly what a multi-entry-point tool needs.
  • Rename hygiene under churn. v6.11 renamed the core loop (quick-dev → build) and merged six skills into one. I grepped every English page for the retired IDs: zero hits. Almost nobody keeps docs consistent through that.
  • A real style guide, followed. docs/_STYLE_GUIDE.md commits to Google style + Diátaxis, with per-doctype templates and checklists — and the published pages mostly honor it.
  • CONTRIBUTING's AI-code policy is ahead of the field. "Using AI to write code is normal here; using AI as a substitute for thinking is not" — plus PR size caps and Discord-first for large changes. Other projects will copy this.

Findings, ranked by impact

F1

Your strongest argument is uncited

HIGH IMPACTSMALL FIX

The Theory of Project Context is the most differentiated page in the docs — and it states precise empirical results ("no improvement in success rate and +20% inference cost", a 53/79/100% pass-rate table, a "709-page wiki" retrieval test) with zero citations. Anyone can check:

$ grep -cE 'https?://' docs/existing-codebases/theory-of-project-context.md 0 # at main@bd7ee16

The claims appear to be real. Two published sources match them exactly and would make the page bulletproof: Gloaguen et al., "Evaluating AGENTS.md" (MemAgents @ ICLR 2026, runner-up best paper: no success-rate improvement, >20% inference-cost increase) and Vercel's agent evals (Jan 27, 2026: 53% baseline / 53% unaided skill / 79% instructed / 100% compressed AGENTS.md index; skill never invoked in 56% of runs; 40KB→8KB). If those are the sources, say so; if not, name the ones that are.

FixReferences section on that one page. I'm happy to open the PR — the maintainers only need to confirm the sources.

F2

The reference tier is one page deep

HIGH IMPACTMEDIUM FIX

Skills and Agents is the entire reference section — one page for 29 named commands (8 core skills, 16 method skills, 5 agents). The machine contracts that orchestrator authors need (Build Auto's status table, blocking conditions, folder+id dispatch) live inside a Build guide; the new layered-TOML config system is documented only in the CHANGELOG; there is no glossary, no troubleshooting hub, and the v4→v6 upgrade guide was folded into the install page while a large v4 install base still exists.

FixA per-skill reference page pattern (the style guide already defines one — "Item Deep-Dive Reference"), a config reference, and a restored upgrade guide. Incremental; I can draft the pattern on one skill first.

F3

Translations are one IA generation behind

MEDIUM IMPACTPOLICY CALL

English moved to the journey structure; all five locales (cs, fr, ko-kr, vi-vn, zh-cn) still ship the old tutorials/how-to/explanation tree, with diverging page sets — 26 to 40 files against English's 29. Several locale redirects land users on English pages mid-journey.

docs/ cs:26 · fr:32 · ko-kr:40 · vi-vn:31 · zh-cn:35 · en:29 (page counts, main@bd7ee16) astro.config.mjs: '/cs/explanation/adversarial-review' → '/build/review-a-change/' # locale → EN

FixDecide the policy explicitly: either migrate locales to the new IA (community sprint) or mark them as best-effort snapshots with a banner. Silent drift is the worst of the three options.

F4

No version signals on an AI-native docs site

MEDIUM IMPACTSMALL FIX

No page says which BMAD version it documents; the site has no changelog surface and no version switcher, while breaking renames ship monthly and a v4 install base reads the same URLs. And for a project whose own docs strategy is "point your AI at the source", the site ships no llms.txt — the one convention built for exactly that audience.

FixA version badge in the header, the CHANGELOG (or release notes) linked in the nav, and a generated llms.txt / llms-full.txt. All three are small PRs.

F5

The docs site's own README is stale

LOW IMPACTTRIVIAL FIX

website/README.md still describes the pre-restructure layout (docs/tutorials/, how-to/, explanation/) that no longer exists. Harmless, but it's the first file a docs contributor opens.

FixOne-file PR; I'll include it with F1.

F6

Small tone drift against your own style guide

LOW IMPACTEDITORIAL

Get Answers About BMad claims bmad-help "handles over 80% of questions" — no source — and closes with a poem. Both are charming; both sit oddly next to a style guide that asks for literal language and no inflated claims. Keep the personality, source the number (or soften it), and maybe let the poem live in the repo rather than the front door enterprise evaluators walk through.

Two notes beyond the docs

M1

Breaking changes ship in minor versions

PROCESS

v6.11.0's changelog opens with a "💥 Breaking Changes" section — renames, removals, a new hard dependency (uv + Python 3.11 for rendered skills). The forwarding shims are genuinely good engineering, but semver says this is v7 territory, and the ecosystem around BMAD (videos, courses, blog posts) rots faster than the docs with every renamed command. If the release train can't slow down, the docs can absorb it: a "renamed in vX" table and version badges (F4) are the mitigation.

M2

The evidence turn is your best story — tell it

PRAISE

v6.9–6.11 quietly rebuilt BMAD's trust model: content-addressed snapshots of exactly what ran, retrospectives that must cite the epic's own artifacts, machine-readable spec statuses, deterministic script cores for sprint planning. That is the most defensible direction in the project and it currently lives only in changelog prose. It deserves a first-class explanation page — "how BMAD produces evidence" — because it's the answer to the hardest enterprise question: how do I audit what the agent did?
