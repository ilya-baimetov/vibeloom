Methodology comparison · v0.3

From spec-driven to contract-driven.

SDD has four flavors — Kiro, Spec Kit, OpenSpec, BMAD. codæ is the next level.

Spec-driven development (SDD) moved AI coding off raw prompting — correctly. codæ pushes the same impulse further: the per-feature specs of SDD become a durable, traceable, approval-gated contract — a graph of mutually-derived specs that governs the lifecycle, not a one-off planning artifact. This whitepaper compares the four main SDD tools at the methodology level and positions codæ against them. Tessl and Pythagora (now Pazi) appear as sidebars.

§1 — Two familiesSpec-driven development, then contract-driven.

Spec-driven development is now a recognized family. AWS Kiro1 turns natural prompts into structured requirements, design, and tasks — anchored in an IDE, now flanked by CLI, web, and cloud surfaces, with steering files and lifecycle hooks. GitHub Spec Kit4 makes specifications executable through a constitution + spec/plan/tasks/implement workflow. OpenSpec6 keeps a persistent spec set in the repository and evolves it through delta-marked change folders — propose, apply, archive. BMAD Method7 organizes ideation through implementation around specialized agents (analyst, PM, architect, developer, UX) and adaptive workflows. Four angles on the same problem.

codæ pushes the same impulse further. A spec isn't enough if it expires after one feature or guides only one generation cycle. The specification stack must become a contract — persistent, derivation-aware, approval-gated, traceable, and used across the lifecycle as both memory and eval surface. VibeLoom is one concrete instantiation — v0.3 is the specification of this level, while the shipped engine implements v0.2; stated so the comparison stays honest in both directions.

SDD asks: how do we make specs better inputs to generation? codæ asks: how do we make contracts the durable control surface of the lifecycle?

This piece compares the four SDD tools at the methodology level — what each treats as source of truth, who governs change, how drift is handled — and shows where codæ extends the family. Tessl and Pythagora remain real participants in the broader landscape but not SDD methodology comparators in September 2026 — one now sells agent-skills infrastructure, the other has left developer tooling altogether. See the sidebars in §9.

§2 — The SDD familyThree flavors of the same impulse.

AWS KiroIDE-anchored SDD.

Kiro is an agentic AI development environment built around three pillars: specs (per-feature triplets of requirements.md — user stories with acceptance criteria — design.md, and tasks.md; bugfix.md for fixes; Requirements-First, Design-First, and gate-free Quick Spec variants; the EARS-notation framing of early Kiro has receded from current docs), steering (persistent project/workspace knowledge in .kiro/steering/*.md with always/conditional/ manual/auto inclusion modes; the AGENTS.md standard is supported as always-on steering), and hooks (event-driven agent prompts or shell commands).1 Task execution is dependency-aware: independent tasks run concurrently in waves.1

The methodology bet underneath: developers will adopt spec discipline when it embeds in the workflow they already live in. Through 2026, "the workflow" stopped meaning just the IDE: Kiro now spans a CLI with third-generation spec runs, spec-review screens, and voice input; opt-in cloud sessions that keep an agent working after you disconnect; a web surface with enterprise SSO; and Crew, a multi-agent orchestration app reachable over messaging channels.3 GA had already added property-based testing for spec correctness, checkpointing, and team plans.2 The spec/steering/hooks spine is unchanged; the surfaces around it multiplied.

GitHub Spec KitConstitution + per-feature artifact bundle.

Spec Kit's official documentation defines spec-driven development as making specifications executable, directly generating working implementation rather than only guiding it.4 The core command flow is /speckit.constitution, /speckit.specify, /speckit.plan, /speckit.tasks, and /speckit.implement, with optional /speckit.clarify, /speckit.analyze, and /speckit.checklist to catch drift and ambiguity at the artifact layer before code is generated. The set keeps growing: /speckit.taskstoissues turns tasks into GitHub issues, and /speckit.converge assesses an existing codebase against its specs.5 Around the core sit 138+ community extensions, 25+ presets, shareable bundles, and a skills mode for agents that prefer skills over slash commands, across 30+ supported agents.4 5

The methodology bet underneath: a constitution plus per-feature executable specs plus extensible process machinery can make AI generation more predictable. The structural gap this paper named in May 2026 — branch-scoped feature artifacts that never compound into a system-level description — is now acknowledged inside the toolkit itself: converge exists to reconcile a codebase with its specs after the fact. The default center of gravity is still the feature bundle, and post-merge persistence remains convention rather than structure.

OpenSpecDelta-spec / change-lifecycle SDD.

OpenSpec, from Fission-AI, is the newest of the four and already at BMAD-scale adoption (52.6k GitHub stars as of September 2026).6 It keeps a persistent requirements set in openspec/specs/ and evolves it through change folders — proposal.md, spec deltas marked ADDED / MODIFIED / REMOVED, design.md, tasks.md — driven by a propose → apply → archive loop, with a longer fluid command set (explore, new, continue, verify). Archiving a change merges its deltas into the persistent specs. The stated philosophy: "fluid not rigid, iterative not waterfall, easy not complex." 30+ AI tools are supported.6

The methodology bet underneath: governance survives only when it is nearly free — a small persistent spec set plus per-change deltas is the most process teams will actually keep using, brownfield included. The structural gap is verification depth: the archive merge is mechanical, drift between spec and code is checked by a verify pass rather than detected as a graph property, and there are no approval gates, derivation links, or semantic drift categories. System-level persistence without lifecycle governance.

BMAD MethodAgent-role / workflow SDD.

BMAD describes itself as an AI-driven development framework spanning ideation and planning through agentic implementation.7 8 v6 installs five named agents — Analyst, Product Manager, Architect, Developer, UX Designer — and roughly two dozen skills across planning and shipping, with one official implementation loop (bmad-sprint-planning → bmad-build → bmad-code-review) plus an unattended worker for orchestrators. BMad Builder allows creating custom agents, workflows, and modules. The framework remains closer to codæ in spirit than the other SDD tools because it governs a broader development lifecycle rather than only single-feature workflow or per-file specs.

The methodology bet underneath: structured agent roles and adaptive workflows can make AI-assisted development behave more like a disciplined team process. The structural gap this paper named in May 2026 — no first-class Contract Graph or trace substrate — needs revising in one half. BMAD's v6.9–6.11 releases grew real run evidence: content-addressed snapshots of exactly what ran, machine-readable spec statuses, and retrospectives required to cite the epic's own artifacts.8 The graph half stands: no item-level derivation, no drift statuses, no reconcile operation. And BMAD's brownfield doctrine now argues the opposite of a durable contract — archive the planning documents, let agents read the code, keep one small verified context block in AGENTS.md.7

§3 — codæ in the pictureContract-driven lifecycle governance.

codæ — instantiated by VibeLoom — turns the specification stack into a contract: persistent, IDed, derivation-aware, approval-gated, traceable, and used as both memory and eval surface. The artifact stack covers intent-specs, product-specs, peer ux-specs, system-specs, context, code, plus traces, review packets, reconciliation packets, and code-sync evidence.

The methodology bet underneath: long-lived AI-generated systems need a durable contract graph, not just better feature specs or workflow prompts. The contract is what a human comprehends; code is downstream. Agent Behavioral Contracts research9 backs this — contract-style enforcement on agents produces measurable governance improvements (5.2–6.8 soft violations per session detected vs uncontracted baselines; 88–100% hard-constraint compliance across 1,980 sessions on 7 models). Not yet proof of full lifecycle governance, but the right shape of mechanism.

codæ is an hommage to Bertrand Meyer's Design by Contract.10 The inheritance is the discipline of explicit obligations between software elements. The boundary moves upward — from routine/class contracts to system-generation contracts. The decidability gap is acknowledged honestly in the manifesto: today's contracts are checked semantically, not boolean. The trajectory is to push more of the contract toward decidability via structural eval and validation runners.

§5 — Cognitive surfaceHow big is the human-mendable surface?

The codæ manifesto's central claim is that the human-mendable surface should be measured in items, not lines of code. Each of the four SDD comparators answers what surface a human is supposed to hold differently:

  • Kiro — per-feature triplet (medium) plus steering files (small, persistent). Mixed-scale; the steering collection plays the role of standing knowledge that survives between features.
  • Spec Kit — small, persistent constitution plus a series of medium-sized per-feature artifact bundles. Mixed-scale; the global surface is what survives between features.
  • OpenSpec — a persistent spec set that compounds with the system, plus small per-change deltas. The delta is the review surface; the accumulated specs/ directory is what a human must still hold as the system grows — persistent, but flat: no tiers, no derivation.
  • BMAD — phase-by-phase artifacts (PRD, architecture, UX, stories) accumulating across the project lifecycle. Larger total surface than the other two, organized by role rather than by graph.
  • codæ / VibeLoom — deliberate, structured stack whose total size scales with mode. vibe intentionally small (compact intent + flat system). expert is the full multi-tier stack — larger, but every tier covers a different abstraction so per-tier cognitive load is bounded.

The right question isn't "which is smaller." It's which sizes for the team and codebase. A team of two doesn't need an expert-mode stack; a multi-team product can't comprehend steering files alone. Cognitive surface is where each tool implicitly picks a target user — and where codæ's mode system addresses more than one target inside one methodology.

§6 — Drift handlingWhat happens to coherence over time?

Drift is the question every spec-driven approach is built around, and the dimension where the four diverge most cleanly:

  • Kiro. Hooks fire on file events to cascade spec changes; property-based testing of specs landed at GA, and the CLI added dedicated spec-review screens in 2026. Steering files carry standing knowledge that outlasts a single feature. Post-completion spec lifetime is mostly convention.1 2 3
  • Spec Kit. Artifact-layer drift detection via /speckit.analyze and /speckit.checklist catches inconsistencies before code generation, and /speckit.converge now assesses an existing codebase against its specs after the fact.4 5 The post-merge gap is narrowing but structural: branch-scoped specs still do not compound into system-level documentation, so drift between features stays invisible at the spec layer until a converge pass is run by hand.
  • OpenSpec. The persistent spec set makes post-merge drift representable: deltas marked ADDED / MODIFIED / REMOVED merge into openspec/specs/ on archive, and a verify pass checks the change.6 But drift is not detected: the merge is mechanical, spec↔code coherence rests on the verify convention, and there are no item-level statuses or semantic checks.
  • BMAD. Workflow correction, "correct course," and readiness gates are built into the agent orchestration; phases re-plan when an upstream artifact changes. v6.9–6.11 added an evidence layer — retrospectives that must cite the epic's own artifacts, content-addressed snapshots of what actually ran.7 8 Drift is still not a graph property, and no status categories exist at item granularity.
  • codæ. Drift forms detected explicitly: stale (downstream depended on changed approved truth), uncovered (approved upstream lacks required downstream realization), dangling (downstream references removed upstream), drifted (semantic mismatch or unflagged direct edit), obsolete (upstream basis superseded conceptually). Reconciliation is a first-class operation with a packet, not an emergent practice.

The honest caveat stands in September 2026: no peer-reviewed benchmark compares drift outcomes across these tools. A June 2026 process taxonomy compares framework shapes13; each drift mechanism is well-described in current docs and practitioner reports; the outcome comparison the field needs still hasn't shipped.

§7 — The bet each makesWhat each is wagering survives.

Underneath every methodology choice is a structural bet about what's worth governing and what should evolve:

  • Kiro bets that an IDE-enforced phase workflow plus steering plus event-driven hooks gives developers the right governance at the right moments. Vindicated if developers want governance built into the tool they already live in.
  • Spec Kit bets that a constitution plus per-feature artifact bundles plus phase-gate analysis is enough governance. Vindicated if most teams' system-level coherence emerges from the constitution rather than from a system-level spec.
  • OpenSpec bets that governance survives only if it is nearly free — a persistent spec set plus delta-marked changes, "fluid not rigid." Vindicated if adoption-through-lightness outlasts formalism as codebases and teams grow.
  • BMAD bets that structured agent roles plus adaptive workflows make AI-assisted development behave like a disciplined team process. Vindicated if the agent-role abstraction scales across project complexity without needing a graph formalism. Its 2026 evidence turn quietly hedges the audit half of that bet.
  • codæ bets that a tiered, mutually-derived contract stack that survives the lifecycle is the only structural answer to drift at scale. Vindicated when, at the tail of a codebase's life — original team gone, multiple agents in parallel, architecture revised — the only artifact a human can still hold is the contract. (See the manifesto for the case.)

§8 — SDD maturity ladderWhere vibeloom fits.

The 2026 SDD taxonomy11 places existing approaches across three rigor levels:

  • Spec-first — specs guide initial development, then drift away from the code that ships.
  • Spec-anchored — specs and code co-evolve with explicit enforcement; the spec doesn't decay because something keeps checking it.
  • Spec-as-source — specs alone are edited; code is regenerated; humans never touch generated code.

The pressure toward the top of the ladder is now visible in the literature too: a July 2026 enterprise framing argues that specification governance — deterministic validation over contract-shaped specs — is the foundation AI-native engineering needs.12

codæ argues for a fourth level: contract-driven. The spec is not one source for one file or one feature; it is the multi-tier, mutually-derived, drift-detecting contract that governs the lifecycle. Same impulse as SDD; larger surface; deeper governance.

SDD maturity ladder, extended. Levels 1–3 are the rigor tiers in Piskala's 2026 taxonomy. Kiro, Spec Kit, OpenSpec, and BMAD all sit at level 2 (different mechanisms — IDE hooks vs phase gates vs delta merges vs role workflows — same family). Within the level, OpenSpec holds the strongest system-level spec persistence and BMAD pushes hardest on the run-evidence axis — the level is compressing upward, but the level-4 slot remains unoccupied by any shipped comparator. Tessl was at level 3 pre-pivot; the January 2026 shift to skills-as-package-manager took it off this ladder (see §9). codæ argues for the fourth level — contract-driven — distinguished by lifecycle governance and graph-based drift detection.

§9 — SidebarsTessl and Pythagora.

Two tools are sometimes grouped with SDD but are not, in September 2026, the right comparators for a codæ methodology discussion — and both moved since the May edition:

TesslAgent-skills registry and enablement, compounding.

Tessl pivoted in January 2026 away from per-file spec-as-source toward "the package manager for agent skills."14 By September 2026 that direction has compounded: the registry versions thousands of skills installed via npx tessl install, every public skill carries a Snyk security score under a March 2026 partnership15, and the company sells an "agent enablement platform" — generate, evaluate, distribute, and optimize agent skills and context — to enterprises such as Cisco and HashiCorp.16 That is skills/context infrastructure, not a feature-spec or contract-stack methodology. Tessl matters here for what it proves: agent context is becoming versioned, evaluated, and secured like software. codæ agrees with that direction — and applies the same lifecycle discipline to system-specific truth rather than distributable skills.

Pythagora → PaziOut of the developer-tool race.

The May edition treated Pythagora as app-generator / AI-developer lineage. That lineage has now left the field: pythagora.ai redirects to pazi.ai, where the same founding team — the creators of GPT Pilot — builds "a platform where autonomous companies are built": role-based business agents with plans and progress reporting, aimed at entrepreneurs rather than engineering teams.17 GPT Pilot remains public but historical. The exit is itself a data point about where the pure app-generation bet led — squeezed between the platform players above and the methodology layer this paper compares, the founders moved up-stack to business operations.
